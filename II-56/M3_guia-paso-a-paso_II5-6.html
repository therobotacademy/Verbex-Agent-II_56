El repositorio en una mirada

El mismo agente del workflow II-4, reescrito como repositorio Python. Misma lógica, distinto contenedor. Cinco ficheros de texto + un paquete verbex/.

verbex-agent/ ├── PERSONA.md · SKILL.md system prompt + few-shots (= SOUL/SKILL de n8n) ├── rules.py R01–R09 como funciones puras ← lo implementas (II-5) ├── main.py orquestador (= grafo workflow) ← lo implementas (II-5) ├── telegram_bot.py trigger: recibe POs por Telegram ├── verbex/ llm.py · persistence.py · notify.py · observability.py ├── dashboard/app.py panel Streamlit sobre los CSV ← II-6 ├── deploy/ start_verbex.bat + Task Scheduler ← II-6 └── data/ Pedidos.csv · Lineas.csv · Errores.csv
Mapa mentalLo que en n8n era un nodo, aquí es una función o un módulo: el SOUL es PERSONA.md; las reglas Code son funciones de rules.py; las hojas Sheets son CSV; el grafo de conexiones es main.py.

II-5 · Implementar y probar

Paso 1 · Prepara el entorno. Copia .env.example a .env y completa al menos ANTHROPIC_API_KEY y TELEGRAM_BOT_TOKEN.
cp .env.example .env # luego edita .env pip install -r requirements.txt python -c "from anthropic import Anthropic; print('OK')"
Paso 2 · Corre los tests (Gate de corrección). En el esqueleto, los 8 tests están en ROJO porque rules.py está sin implementar. Tu objetivo: ponerlos en VERDE.
pytest tests/ -v # 8 passed in 0.03s ← cuando termines
Cada test reproduce uno de los 8 casos de prueba que validaste en el nodo Code de n8n.

II-5 · Probar una regla y completar el pipeline

Paso 4 · Juega con una regla en el shell. Abre Python y prueba una regla aislada — entra un dict, sale un dict.
import rules po = {"numero_pedido":"PO-T","cliente":{"codigo_erp":"STRA-001"}, "lineas":[{"linea_id":1,"part_number_cliente":"ST9-HTP-RIB-047", "cantidad":5,"unidad":"EA","fecha_entrega_requerida":"2026-12-01"}], "estado_normalizacion":"COMPLETO","confianza":0.55,"alertas":[],"aog":False} print(rules.aplicar_reglas(po)["estado_normalizacion"]) # PARCIAL (R03)
Paso 5 · El LLM extrae una PO de texto libre. Requiere ANTHROPIC_API_KEY.
from verbex import llm po = llm.normalizar("Purchase Order PO-2025-STRA-0847. Stratos Systems.\n" "Part: ST9-HTP-RIB-047, Qty: 12 EA, Need Date: 15/09/2025. CoC required.") # "15/09/2025" → "2025-09-15"; PN cliente → VBX-COMP-4471-B; confianza 0.97
El parser anti-alucinación de llm.py verifica que el PN proveedor exista en la tabla; si el LLM inventa uno, lo anula y añade una alerta.

Paso 7 · Anti-duplicado (R09). Envía la misma PO dos veces: la segunda, persistence.es_duplicado() devuelve True, el orquestador avisa al operador y detiene el pipeline. No se reescribe ni se renotifica.

II-6 · Operar y desplegar

Un workflow que funciona no es todavía un sistema operable. Operable = se observa, se recupera de fallos y deja rastro auditable.

Paso 10 · Observabilidad. El agente ya registra eventos en logs/verbex.log y los fallos técnicos en data/Errores.csv vía verbex/observability.py — el equivalente del Error Trigger Workflow de n8n, en ~30 líneas de la stdlib.

Paso 11 · Dashboard (read-only sobre CSV). Lee los mismos CSV que escribe el agente. Sin credenciales, sin Sheets.
pip install -r dashboard/requirements.txt python -m streamlit run dashboard/app.py # → http://localhost:8501
5 KPIs (POs totales · hoy · AOGs · tasa de éxito · errores 7d) · filtros por programa/estado/prioridad · tabla de últimas POs con detalle de líneas · pestaña de errores.
Paso 12 · Deploy (2 procesos, doble clic). deploy/start_verbex.bat arranca el bot y el dashboard, cada uno en su ventana. deploy/task-scheduler.md lo automatiza al iniciar sesión en Windows.
